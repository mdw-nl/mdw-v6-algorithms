# Dev network

A local vantage6 network for testing images end to end (AGENTS.md §5): a server, the
vantage6 UI, (best-effort) our own algorithm store, a local Docker registry, and one
organization per entry in a scenario file -- some with a running node, at least one
without.

## Quick start

```bash
bash dev-network/scripts/up.sh                  # SCENARIO=healthy by default
SCENARIO=faulty bash dev-network/scripts/up.sh  # or another scenario
bash dev-network/scripts/status.sh
bash dev-network/scripts/down.sh
bash dev-network/scripts/reset.sh               # down + wipe state + up
bash dev-network/scripts/push_image.sh <image-name> <tag>   # push a local image to the dev registry
```

`up.sh` is idempotent: running it again while the server is already up is a no-op.
All the real logic lives in `scripts/devnet.py` (a plain Python script using
`subprocess` to call the pinned `v6` CLI and `docker` -- no separate orchestration
tool); the `.sh` files are thin wrappers so Makefile targets and direct shell use look
the same.

## Layout

- `scenarios/*.yaml` -- declarative: which organizations exist, which datavalgen
  profile (see `datavalgen/schemas/`) each live node mounts as its `default` database,
  and which organization has no node running at all. Add a new scenario by adding a
  new file here; the scripts never need to change.
- `generated/` -- gitignored. Server/store/node configs and the entities import file,
  regenerated by every `up`/`reset`.
- `config/` -- intentionally empty for now; every config is templated in
  `devnet.py` rather than kept as static files, because every value in them (ports,
  the collaboration name, the docker0 bridge IP) is already a Python constant at the
  top of that script. If a future need calls for genuinely static config (e.g. an
  `--extra-node-config` snippet), put it here.

## What's running

| Component | How | Port |
|---|---|---|
| Server | `v6 server start` (pinned `server-lite:4.14.0-rc8` image) | 7601 |
| UI | plain `docker run` of the `ui` image | 7600 |
| Algorithm store | `v6 algorithm-store start` -- **best-effort, see below** | 7602 |
| Local registry | `registry:2` | 5151 |
| Nodes | `v6 node start` per organization with `node: true` in the scenario | (node-internal) |

Admin login: `dev_admin` / `ior8ahP7ahqu3ees` (dev-only, fake, committed on purpose --
never reuse these anywhere else). Each organization also gets its own
`<name>_user` / `<name>-ior8ahP7ahqu3ees` login. Collaboration name: `mdw-dev`.

## Known gap: the algorithm store

AGENTS.md §5 calls for "our own algorithm store." The orchestration for this is fully
implemented (`_try_start_store`/`link_store_to_server` in `devnet.py`, using the image
name vantage6 itself defaults to -- `vantage6.common.globals.DEFAULT_ALGO_STORE_IMAGE`,
i.e. `infrastructure/algorithm-store:<tag>` on whatever registry you point it at), but
**it could not be validated in this sandbox**: MDW's `ghcr.io/mdw-nl/vantage6/infrastructure`
mirror has not published an `algorithm-store` image (only `server-lite`, `node-lite`,
`ui`), and the upstream community image lives on `harbor2.vantage6.ai`, which this
sandbox's network cannot resolve at all (DNS failure, not an auth/image-tag problem).

`up.sh` treats this as best-effort: if the store image can't be pulled or the
container doesn't become healthy, it logs a clear warning and continues bringing up
the server, UI, nodes and registry normally -- a missing store never blocks the rest
of the network. Once either MDW publishes `infrastructure/algorithm-store` on
ghcr.io, or this environment can reach `harbor2.vantage6.ai`, no code change should be
needed -- just confirm the image pulls (`docker pull <STORE_IMAGE from devnet.py>`)
and rerun `reset.sh`.

## Why not `v6 dev create-demo-network` / `start-demo-network`

That's vantage6's own all-in-one dev-network command and was tried first. Its
`create-demo-network` runs the server import through a separate, short-lived
container; in this environment that import did not persist into the same database
file the subsequently-started persistent server reads from (the server came up with
only the bootstrap `root` organization -- every other organization, user and node
record from the import was missing). It also only supports one shared dataset
auto-split evenly across all nodes, not a different datavalgen profile per node,
and has no "register an organization with no node" option. `devnet.py` instead forks
the proven pattern from the sibling repo `v6-infrastructure-sh/infrastructure/
{setup,shutdown,functions}.sh`: start the server, then `docker cp` the entities file
into *that* running container and `docker exec ... vserver-local import` inside it --
guaranteeing the import lands in the exact database the server is already using.

## Scenarios

- `healthy`: `alpha`/`gamma` on the `healthy` profile, `beta` on `skewed`, `delta`
  has no node.
- `faulty`: `alpha` on `broken`, `beta` on `few_events`, `gamma` on `healthy`,
  `delta` still has no node.

Both always include the node-less `delta` organization, since AGENTS.md §5 requires
it in every scenario, not only "faulty".
